# AWS Phase 1 environment (staging)

An isolated copy of bizinsights on AWS, for checking sign-in on Amazon Cognito. It is separate from
production (`infra/cdk`, [aws-deployment.md](aws-deployment.md)); nothing here touches it.

```
browser ─► Lambda function URL (HTTPS) ─┬─ /api/*  ─► the API (same Hono app as production)
                                        └─ others ─► the web UI (Next.js export, in the package)
the function ─► Cognito (insights-auth-staging) · RDS PostgreSQL · DynamoDB (rate limits, sign-in state)
             ─► Secrets Manager (at cold start) · CloudWatch Logs (/aws/lambda/insights-staging)
```

| Piece | Where | Notes |
| --- | --- | --- |
| Function | `apps/aws` (entry `src/index.ts`), `pnpm --filter @app/aws build` → `apps/aws/dist/function.zip` | Node 22, arm64, 1 GB. The same API code as production: DynamoDB for the coordinator (`dynamoCoord.ts`), secrets from Secrets Manager (`secrets.ts`), the static UI served from the package (`staticSite.ts`). |
| Infrastructure | `infra/aws/staging.yaml` + `infra/aws/cognito.yaml` | Deployed together by `infra/aws/deploy-staging.sh`. |
| Database | RDS PostgreSQL 17, db.t4g.micro, 20 GB gp3, encrypted, TLS required | Migrations run by the function (`{"action":"migrate"}`), recorded the way `prisma migrate` does. |
| Secrets | `insights/staging/app` (generated by the script), the Cognito stack's secret, RDS's own master-user secret | Never in the function's environment, never printed. |
| Monitoring | Log group `/aws/lambda/insights-staging` (30 days); alarms `insights-staging-auth-unavailable`, `insights-staging-function-errors` | |

Not run here (Phase 1 is sign-in only): Shopify sync, webhooks, scheduled jobs and app emails
(invitations, alerts). Jobs sent to a queue are logged and dropped. Sign-in emails are Cognito's.

## Cost

About US$20-25 a month in ap-southeast-2, almost all of it the database (db.t4g.micro and its
storage); Lambda, DynamoDB and logs stay within the free tier at this use, Secrets Manager is
US$0.40 per secret, alarms US$0.10 each. Deleting both stacks stops all of it (the database leaves a
final snapshot, which costs storage until deleted).

## Deploy

1. Build the package on a development machine: `pnpm --filter @app/aws build`.
2. In the AWS console, open CloudShell in the target region and upload `apps/aws/dist/function.zip`,
   `infra/aws/staging.yaml`, `infra/aws/cognito.yaml` and `infra/aws/deploy-staging.sh`.
3. Run it with the commit the package was built from:

```bash
COMMIT=<git sha> bash deploy-staging.sh
```

It creates or updates everything, runs the migrations, smoke-tests the URL and prints the
environment's details (URL, user pool, client, domain, callback and logout URLs).

## Security trade-offs of this environment

- The function runs outside a VPC (Cognito's sign-in endpoints need the internet, and a NAT gateway
  would cost more than the rest together), so the database accepts connections from the internet.
  TLS is enforced by RDS (`rds.force_ssl`) and verified by the app against Amazon's CA, and the
  password exists only in Secrets Manager. Production (`infra/cdk`) uses private subnets and a NAT.
- The function URL is public (it is a website); `lambda:InvokeFunction` is granted only through the
  URL (`InvokedViaFunctionUrl`), so maintenance actions like `migrate` need the account's own IAM access.
- The client's address used for rate limits is Lambda's `sourceIp`; an `x-insights-client-ip` header
  from the client is replaced.

## Remove

```bash
aws cloudformation delete-stack --stack-name insights-staging
```

```bash
aws cloudformation delete-stack --stack-name insights-auth-staging
```

The user pool is kept (DeletionPolicy Retain) and must be deleted in the Cognito console; the two
secrets are deleted after their recovery window (`aws secretsmanager delete-secret`).
