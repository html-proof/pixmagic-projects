# Security model

Audits: [2026-10-10](security-audit-2026-10-10.md) and [2026-10-14](security/SECURITY_AUDIT.md)
([implementation](security/SECURITY_IMPLEMENTATION.md), [tests](security/SECURITY_TEST_RESULTS.md),
[deployment checklist](security/SECURITY_DEPLOYMENT_CHECKLIST.md)).

| Concern | Control | Where |
| --- | --- | --- |
| SaaS identity | Amazon Cognito user pool, spoken to only by the API (backend-for-frontend): no Cognito token ever reaches page JavaScript. Its ID token is verified server-side (RS256 pinned, the pool's JWKS, issuer, audience = our confidential app client, `token_use`, expiry, and a nonce for Google) before anything else happens. Our own session: HMAC-signed, httpOnly, SameSite=Lax, Secure cookie (5 days) + the Cognito refresh token AES-256-GCM encrypted (bound to the identity) in an httpOnly cookie sent to `/api` only; re-checked with Cognito every minute (disabled, deleted or signed-out-everywhere users lose the session; Cognito unreachable does not sign anyone out; a session due for that check without its refresh-token cookie ends, so the session cookie alone can't outlive anything done in Cognito). A session whose sign-in method is no longer the account's (removed in Settings, or by a take-over) ends on its next request. Signing out retires that session id until it would have expired and revokes that device's refresh token; "sign out everywhere" and password changes/resets move `users.sessions_valid_after` and end every Cognito refresh token | `apps/api/src/cognito.ts`, `session.ts`, `context.ts` (`loadUser`) |
| CSRF | SameSite=Lax + Origin check on every cookie-authenticated non-GET; sign-in/sign-up endpoints check Origin even without a cookie (login CSRF) | `apps/api/src/app.ts`, `context.ts` (`requireAppOrigin`) |
| CORS | No CORS headers anywhere except the public web pixel (`*`, no credentials), so browsers never let another origin read the API | `routes/pixel.ts` |
| Emailed codes | Sign-up confirmation, password reset, email change/verification and (when switched on) passwordless sign-in codes are Cognito's own (generated, stored, expired and limited by Cognito); on top, per-IP and per-address limits on sending and per-IP limits on guessing; answers never say whether an account exists (Cognito `PreventUserExistenceErrors` plus identical responses) | `routes/auth.ts`, `rateLimit.ts`, `infra/aws/cognito.yaml` |
| Google | Cognito managed login, authorization code + PKCE (S256) + nonce, `identity_provider` sent so no Cognito page shows; state single use (the coordinator: a DynamoDB table) and bound to the browser that started it (`__oauth` cookie: no login CSRF); the code is exchanged server-side with the client secret; a federated account is linked to an existing one only on a provider-verified email, and when that account's own address was never verified the verified sign-in takes it over (its other Cognito users deleted, every session ended, and what its opener set up undone: API keys they made and access and invitations they gave revoked, workspaces they made or claimed left; what workspace owners gave the address stays: no account pre-hijack through a copied invitation link); no account is created from an address Google hasn't verified; only a sign-in, or a verification code, that proves the account's own address marks it verified (a Google account linked under another address, or a code from an email change to another inbox, never does), and an account nobody has proved can't change its address; linking Google from Settings starts with a POST from our own pages (no other site can start it) and always shows Google's account chooser (`prompt=select_account`), needs the account's own session at both ends, a sign-in in the last 15 minutes or the password just now, and a verified address, refuses a Google account another account uses, and is emailed to the account's address (so is a password added there, and any method removed); a Google session stands in for the person (removing a method, deleting the account, adding a password) only when it proved the account's own address: one linked under another address needs the account's password; a Google account removed in Settings never links back by its address until linked again there; every redirect back is checked as the browser will resolve it (dot segments included) | `routes/auth.ts`, `routes/account.ts`, `identity.ts` |
| HTTPS | CloudFront redirects plain http to https, for pages and the API. HSTS on pages and on API responses over https. The function URL behind CloudFront answers API requests only when they carry CloudFront's secret origin header, so nothing reaches the API around CloudFront and WAF | `infra/cdk/lib/app-stack.ts`, `apps/aws/src/index.ts`, `apps/api/src/app.ts` |
| Two-step verification | Opt-in TOTP (an authenticator app) for password accounts, Cognito's own (`MfaConfiguration: OPTIONAL`, `SOFTWARE_TOKEN_MFA` only: accounts without it sign in as before). Setting it up needs a recent sign-in or the current password; turning it off needs the password and a current code, checked as a sign-in checks them. At sign-in Cognito's challenge session stays in the coordinator for its three minutes, named by a random httpOnly cookie; codes are limited per IP and per account on top of Cognito's own limit | `routes/auth.ts` (`/auth/login/mfa`), `routes/account.ts`, `infra/aws/cognito.yaml` |
| Passwords | Never stored by us: Cognito holds them (salted hash). They pass through the API on sign-in (USER_PASSWORD_AUTH) and are never logged, and go to no one but Cognito (the Firebase password check of the migration window was removed on 2026-10-18). Signing up again over an unconfirmed sign-up with another password replaces it, and the code decides whose password stays: the sign-up page sends its password with the code, and a confirmed sign-up whose password isn't that one gets it (the old one's Cognito tokens and sessions end; a password Cognito wouldn't take leaves none), so nobody who typed someone's address keeps a password on the account its inbox's owner confirms. An address held by a password user that never proved it (an account opened for someone else's address) isn't locked to its owner: their sign-up or password reset gets a code we email ourselves (Cognito sends none to an unverified address; only an HMAC of it is kept, five guesses an hour), and entering it replaces that password user with theirs and takes the account over. API keys and invitation tokens are 240/256-bit random and stored as SHA-256 only | `routes/auth.ts`, `routes/workspaces.ts` |
| Shopify OAuth | Domain normalisation, query HMAC, timestamp window, single-use state in the coordinator + browser cookie, same-user check | `routes/shopify.ts` |
| Shopify tokens | Expiring offline tokens (1-hour access, 90-day refresh, rotated under a lock); AES-256-GCM with per-store AAD; versioned keys for rotation; never returned by the API or logged | `packages/core/src/tokens.ts` |
| Secrets | Secrets Manager only (locally `apps/aws/.env`), set with `infra/cdk/scripts/put-secrets.mjs` (which never prints a value) and read at cold start, never from the functions' environment (anyone who can read a function's configuration sees that) or the UI bundle (the UI has no settings at all). The Cognito app client secret is in its own secret, readable by the API function only. Cognito's admin calls (five actions, on this one pool) are signed with the API function's own role: no access keys anywhere. In production the app refuses to start if `SESSION_SECRET`, `OTP_PEPPER` or `TOKEN_ENCRYPTION_KEYS` still holds a placeholder or test value from this repo, or with a Cognito emulator configured | `apps/aws/src/secrets.ts`, `infra/cdk/lib/auth-stack.ts`, `packages/core/src/env.ts` |
| Webhooks | Raw-body HMAC (constant-time compare), unique delivery id (duplicates acknowledged once processed), queued processing; a body that names its shop must match the unsigned shop header, and the destructive topics (`app/uninstalled`, `shop/redact`, `customers/*`) must name one; a client's custom-distribution app only vouches for that client's store | `routes/webhooks.ts` |
| Tenant isolation | (1) membership check → 404 for non-members; (2) every query filters by workspace; (3) Postgres RLS on all tenant tables via `app.workspace_id` for the `app_rls` role, with a test that fails any new tenant table without it | `context.ts`, `packages/db`, `migrations/*_rls`, `apps/api/test/security.test.ts` |
| Authorization | Role matrix owner/admin/analyst/viewer, enforced server-side per route. OAuth callbacks (Shopify, ads) re-check the role when the platform sends the person back. Removing or demoting a member below `apikeys:manage` revokes the API keys they made; pending invitations can be cancelled; owner changes are serialized (no ownerless workspace) | `packages/shared/src/roles.ts`, `routes/workspaces.ts` |
| Staff Management | Supervisors see only their assigned employees (scope ANDed with every filter); pay settings (rates, overtime/break policies, currency) need `pay:manage`; nobody but the owner edits/approves their own hours or pay, and whoever submits a payroll can't approve it; database triggers freeze approved shifts, their breaks and finalized payroll items | `packages/core/src/staff/*`, migrations `*_staff_management`, `*_security_hardening` |
| API keys | `sk_live_` + 240 bits, SHA-256 hash stored, shown once, read-only, workspace-scoped, revocable | `routes/workspaces.ts` |
| PII | No customer names/emails/addresses stored; customer id → keyed HMAC only with `read_customers`; contact details fetched live and sent `no-store`; GDPR webhooks handled | `persist.ts`, `routes/contacts.ts`, worker |
| WhatsApp PII | Only when a store connects WhatsApp: customer WhatsApp number + first name AES-256-GCM encrypted (AAD `wa:<storeId>:<kind>`), keyed HMAC for lookup, masked in the UI; send details encrypted and cleared once sent; retention purge; customers/redact + shop/redact delete it | `packages/core/src/whatsapp/*`, docs/whatsapp.md |
| WhatsApp webhooks | `X-Hub-Signature-256` HMAC of the raw body with the app secret, verified before anything is applied; a manual connection's own secret vouches only for that connection (not others on the same WABA); preference changes reach only the store whose number they name; a START older than the last consent change is ignored; unsigned deliveries are rate limited before parsing; GET handshake needs the verify token | `routes/whatsappPublic.ts`, `webhook.ts` |
| Email integrations | OAuth (Google `gmail.send`, Microsoft delegated `Mail.Send`) with PKCE, single-use state bound to the browser and the person, exact redirect URIs, membership re-checked in the callback; tokens and SMTP passwords envelope-encrypted (per-secret data key wrapped by `EMAIL_CREDENTIAL_KEYS`, AAD per row and purpose), never returned or logged; refresh under a Coordinator lock with compare-and-set; SMTP TLS/STARTTLS only, host and every resolved address checked against private/loopback/link-local/metadata ranges before each connection; templates sanitized (allowlist) on save and after rendering, placeholders only (no code); previews in a sandboxed iframe; rules a bounded declarative tree; composite `(id, workspace_id)` foreign keys between email tables; recipients encrypted + keyed hash + masked; append-only delivery events; event API keys (`ek_live_`, SHA-256 stored) can only post events to their own workspace | `packages/core/src/email/*`, `packages/shared/src/email/*`, `apps/api/src/routes/email*.ts`, docs/email.md |
| Tracking/review links | 24-byte random tokens, only their SHA-256 is looked up; expire after 120 days; `noindex`, `no-referrer`; per-IP rate limits | `routes/whatsappPublic.ts` |
| SSRF | Outbound requests go only to fixed AWS Cognito/Google/Microsoft hosts, `*.myshopify.com` (validated), Shopify's bulk-result link (HTTPS only) and Meta's `paging.next` (pinned to graph.facebook.com: it carries the token). The one user-chosen destination, an SMTP server, is limited to ports 465/587/2525 with TLS, and its name and every address it resolves to (DNS over HTTPS) must be public unicast; checked again before each connection. The functions run in private subnets, and the only thing in the VPC that accepts their connections is the database | `cognito.ts`, `packages/core/src/shopify.ts`, `apps/worker/src/bulkOrders.ts`, `infra/cdk/lib/data-stack.ts` |
| Ad platform tokens | AES-256-GCM, never returned; PKCE for Google; state single-use and bound to user, workspace and store; syncs pause while the store is uninstalled; the platform grant is revoked when the store's data is purged (unless another store relies on it) | `packages/core/src/adConnections/credentials.ts` (encryption), `adConnections/connect.ts` (state, revoking), `persist.ts` |
| Pixel | Public ingest key; events older than 48 h (production) or in the future are dropped; paths ≤ 512 chars; dedupe ids pruned after 3 days | `routes/pixel.ts`, `apps/worker/src/index.ts` |
| Abuse | AWS WAF at CloudFront: 1,500 requests a minute per IP (one address is often an office or a mobile carrier) on `/api/*` (webhooks and the pixel exempt), Amazon's IP reputation and known-bad-inputs rules. Behind it the same 1,500/min/IP in the app (`globalLimit`, on the coordinator) plus per-key limits for sign-in, codes, invitations (per workspace and per sender), workspace/API-key creation, contacts, refresh, store connections, staff analytics and exports, WhatsApp estimates and the pixel, all in one table. 429s carry `Retry-After`. The client IP is the address CloudFront saw, passed to the API as `x-insights-client-ip` only on requests that carry the origin secret; anything a client sends under that name is dropped | `infra/cdk/lib/edge-stack.ts`, `apps/aws/src/index.ts`, `apps/api/src/rateLimit.ts` (`LIMITS`) |
| Logs | JSON logger redacting credential fields (case-insensitive, any depth) and scrubbing tokens and email addresses out of messages and errors | `packages/core/src/logger.ts` |
| Errors | Unhandled errors return a generic 500 (a 503 "try again" when the database is unreachable); stack traces stay in logs | `apps/api/src/app.ts` |
| Audit | Security-relevant actions recorded per workspace, with the request's IP, and before/after values for pay changes; append-only (a trigger refuses edits; the tenant role can't delete); sign-ins are logged with the user id. Account-level events (account created, sign-in identity linked or removed, an unverified account taken over by a verified sign-in (with what was undone), a claim of an address nobody proved started or completed, an unconfirmed sign-up replaced, a confirmed sign-up's password replaced by the code's owner, an account from before Cognito given its Cognito user, password reset or changed, email changed or verified, two-step verification turned on or off, signed out everywhere, account deleted) in `auth_events` | `audit_logs`, `auth_events` (`apps/api/src/identity.ts`), migration `*_security_hardening` |
| Headers | UI: HSTS, `X-Frame-Options: DENY`, CSP `frame-ancestors 'none'; base-uri 'self'; object-src 'none'; form-action 'self'` (enforced) plus a full allowlist CSP in Report-Only (outside origins: only Meta's SDK and frames for WhatsApp sign-up, and Cloudflare's analytics beacon; Google sign-in is a full-page redirect, so it needs none), COOP `same-origin-allow-popups`, nosniff, referrer and permissions policies. API: nosniff, `Cache-Control: no-store`, CSP `default-src 'none'`, `X-Frame-Options: DENY`, HSTS over https | `apps/web/public/_headers` (applied by `apps/aws/src/staticSite.ts`), `apps/api/src/app.ts` |
| Source maps | Not produced for the browser (Next.js default) or for the functions (`sourcemap: false`) | `apps/web/next.config.ts`, `apps/aws/scripts/build.mjs` |
| Dependencies | `pnpm audit` clean and enforced in CI (`--audit-level high`); vulnerable transitive build tools pinned up through `pnpm.overrides` | `package.json`, `.github/workflows/ci.yml` |
| Database roles | `app_rls` (every tenant request) has RLS on every tenant table, no write access to `users`, and append-only `audit_logs` | `infra/postgres/init.sql`, migrations |

## Database credentials and network exposure

`docker-compose.yml` publishes every port on the loopback addresses only. A bare `"5434:5432"`
listens on all interfaces, and Docker Desktop's Windows firewall rule admits it on every network
profile, so anyone on the same Wi-Fi (or on this PC's Mobile Hotspot) could log in to Postgres.

`POSTGRES_PASSWORD` and the `app_rls` password in `infra/postgres/init.sql` are development
defaults. Any database reachable from somewhere else needs real ones. To change them on a running
database:

```sql
ALTER ROLE app PASSWORD '<new owner password>';
ALTER ROLE app_rls PASSWORD '<new tenant password>';
```

Local tools that connect directly (`DATABASE_URL`, `APP_DATABASE_URL`, the tests' `TEST_PG_PORT`
database) need the new passwords too.

On AWS neither is a default: RDS generates the owner's password into Secrets Manager
(`insights/<environment>/db-owner`), `put-secrets.mjs` generates `APP_RLS_PASSWORD`, and the
`migrate` action sets the `app_rls` role's password from it. The database is in isolated subnets,
not publicly accessible, accepts 5432 only from the functions' and the admin host's security
groups, and requires TLS (`rds.force_ssl`), which the app verifies against Amazon's CA
(`infra/cdk/lib/data-stack.ts`, `apps/aws/src/secrets.ts`). The old deployment's database on the
owner's PC was created with the development defaults; it goes when that deployment is retired
([aws-deployment.md](aws-deployment.md#retiring-the-old-cloudflare-deployment)).

The owner role `app` is the RDS master user (a member of `rds_superuser`). The system paths
(webhooks, jobs, auth bootstrap) use it, so it can do anything in the database. Moving those paths
to a narrower owner is tracked in [the 2026-10-10 audit](security-audit-2026-10-10.md).
