- **Step 17 - the dynamic optional-scope request flow.** Built the mechanism that was the second half of Step 14's "re-enable the customer and funnel modules, in this order" - the one the tomls, `appConfig.test.ts` and `docs/shopify-setup.md` all said did not exist. Approval is now the *only* remaining gate; no further code is needed on our side.
  - **The shape of the thing, and why it isn't a callback.** The app is `embedded = false`, so App Bridge's `shopify.scopes.request()` is unavailable and the merchant goes to Shopify's request URL, `https://admin.shopify.com/store/<handle>/oauth/install?client_id=…&optional_scopes=…` (verified against Shopify's "Manage access scopes" page, not assumed). **It takes no `redirect_uri` and no `state`, and returns no authorization code** - Shopify records the answer and then opens our `application_url` with nothing to say what happened. So the grant is *learned*, never received, by two independent paths: the `app/scopes_update` webhook (covers a merchant who grants and never returns, or who changes scopes in their admin), and `POST .../scopes/refresh`, which queries `currentAppInstallation { accessScopes }` and which the dashboard calls once on the merchant's return so the module unlocks immediately instead of whenever the webhook lands. Anything built on getting an answer back on that redirect would have been built on sand.
  - **Granting a scope does not backfill the data behind it**, and one case fails silently rather than loudly. `read_customers` changes what the orders query asks for (`includeCustomer`), so every order already imported carries no customer hash: "New vs returning" would have read as 100% new - worse than the module staying locked. Both paths therefore queue `scopeFollowUpKinds`: a **full** orders re-import for `read_customers` (the gap is the whole history, not recent days) and `install_pixel` for `write_pixels`, since that scope only grants permission to create the pixel and nothing had created it. - **Step 18 - giving optional scopes back, and the "flaky suites" that were not flaky.** Two things: `appRevokeAccessScopes`, which Step 17 left unbuilt, and a retraction of Step 17's last bullet.
  - **The integration suites were never flaky; concurrent runs were destroying each other.** `resetDb` truncates every table between tests, and nothing stopped two runs doing that to the same `app_test` database. Instrumenting the truncate with its process id and sampling `pg_stat_activity` caught four vitest workers from different runs truncating and inserting at once, including a mutual block: `BLOCKED 154003 /* RESETDB pid=23900 vt=1 */ TRUNCATE … BY 154078 /* RESETDB pid=1476 vt=5 */ TRUNCATE …`. That accounts for every reported symptom - `store.create()` failing with "write conflict or deadlock", `findUniqueOrThrow` not finding a user created two lines earlier, a different count each run - and for why it looked pre-existing: the damage lands on whichever tests happen to be running. Run alone, the API suite passed 7/7 and the worker suite 4/4, counts stable. The second run was the previous session's own measurement harness leaving background runs behind; **CI runs the suites one at a time and was never a coin toss.**
  - **The collision is now impossible instead of silent, and counting connections could not have done it.** The first fix here waited for the test database to go quiet and then refused; that is unsound, because vitest starts a fresh worker per test file and Prisma closes its pool when the file ends, so a run has no connections open about half the time and a second run sampling one of those windows would have started anyway. `lockTestDatabase` (`packages/db/src/testing.ts`) instead holds a session-level advisory lock for the whole run, taken in the *maintenance* database so it can be held before the test database exists - `migrate:deploy` creates it, and two runs migrating at once corrupt `_prisma_migrations`. Postgres drops the lock when the connection goes, so a killed run leaves nothing to clear up; a waiting run names who holds it, and orphaned workers still connected to the test database are reported rather than raced. `test-support/globalSetup.ts` takes the lock, migrates, applies grants, and returns the unlock as vitest's teardown. The lock is deliberately **not** in `test:prepare`, which the e2e setup shares: Playwright starts the Worker before its global setup, so a connection is legitimately already open there. `TEST_DB=<name>_test` remains the way to run two suites at once, documented in `docs/local-dev.md`.
  - **Revoking is the asymmetric half of requesting, and the asymmetries are the design.** Only scopes that are declared optional *and* currently granted are sent on (`revocableScopes`): a required scope is part of the install grant and Shopify will not take it back, so the API answers `scope_unavailable` rather than relaying a `userErrors` entry. There is no merchant round trip - a revoke is the app's own call and takes effect immediately. Unlike `requestableScopes` it does **not** treat a granted `write_X` as covering `read_X`: you can only hand back a handle that was actually granted.
  - **A Shopify refusal arrives looking like success.** `appRevokeAccessScopes` reports problems in `userErrors` inside an HTTP 200 with no GraphQL error, so a caller checking only for those would record a revoke that never happened. `revokeAccessScopes` throws `ScopeRevokeError` on a non-empty list (→ 409 `scope_not_revocable`, stored scopes untouched, nothing audited); a Shopify that does not answer is still a 502.
  - **The stored scopes are reconciled, not edited.** After the mutation the route re-reads `currentAppInstallation` exactly as `refresh` does, because `grantedScopes` is a cache and the authoritative answer is one call away - which also records the change once, in the existing `store.scopes_updated` shape, now tagged `via: "revoke"`. The locked module then offers **Enable** again, so a revoke is reversible by the merchant. A reconcile that fails is explicitly not reported as a failed revoke - the scope is already gone at Shopify, so the route falls back to subtracting what Shopify said it took and writes that, because leaving the cache alone would keep the dashboard offering a module whose scope the token no longer has. What it does not do: it does not delete data the scope let us import, and it does not remove a web pixel `write_pixels` allowed us to create.
